## 1. Alternativas de Stack Evaluadas

Se evalúan 3 alternativas de stack mediante criterios multidimensionales, alineados con los objetivos de escalabilidad, perfil del equipo y bajo consumo energético.

| Criterio                           | Alternativa 1: MEAN (Node/Express + Flutter + MongoDB) | Alternativa 2: Node/Express + Flutter + PostgreSQL | Alternativa 3: Java Spring Boot + Flutter + PostgreSQL |
| ---------------------------------- | ------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------------ |
| Curva de Aprendizaje               | Baja-Media (Node/TS + Flutter/Dart)                               | Baja-Media (Node/TS + Flutter/Dart)                | Alta (Verboso, fuertemente tipado)                     |
| Costo de Infraestructura           | Moderado (Node async I/O)                              | Moderado-Bajo (Node async I/O)                     | Alto (Mayor consumo memoria JVM)                       |
| Soporte Comunitario                | Masivo / Muy Alto                                      | Masivo / Muy Alto                                  | Masivo / Corporativo consolidado                       |
| Eficiencia Energética / Eco-Design | Media                                                  | Media-Alta                                         | Media-Baja (Warm-up JVM)                               |
| Idoneidad para Optimización        | Media (cómputo matemático en JS)                       | Media-Alta (JS/TS con librerías)                   | Media (JVM, ecosistema robusto)                        |
| Madurez Empresarial                | Alta (Flutter)                                         | **Alta (Flutter + Express)**                       | Alta                                                   |
| Puntaje                            | 3.8                                                    | **4.4**                                            | 3.4                                                    |

## 2. Alternativa Seleccionada

**Alternativa 3: Java Spring Boot + Flutter + PostgreSQL**

> Cambio respecto a V_1_3_0 (que seleccionaba Node/Express): el backend
> implementado y verificado es Spring Boot (ver ADR-07 en DOC-012).
> La tabla de evaluación del §1 se preserva como historial de la decisión.

### 2.1 Lista de Justificaciones

La selección de la combinación **Java (Spring Boot) + Flutter + PostgreSQL** se sustenta en las siguientes justificaciones:

1. **Frontend multi-plataforma (Flutter/Dart):** Flutter usa Dart, un lenguaje de tipado estático con hot reload y compilación nativa, que permite construir con una sola base de código la web del operador, el dashboard y el modo conductor móvil, acelerando el desarrollo del MVP en las 14 semanas.

2. **Spring Boot como backend único y maduro:** Spring Boot 4.1 con Java 17 es un framework consolidado con seguridad (Spring Security + OAuth2 Resource Server), validación (Bean Validation), persistencia (Spring Data JPA), migraciones versionadas (Flyway) y documentación OpenAPI integradas, ideal para la API REST del sistema. Se usa como **único backend**.

3. **Tipado estático en todo el stack:** El frontend Flutter usa **Dart** (lenguaje de tipado estático con null safety) y el backend usa **Java** (tipado estático con records y validación declarativa), manteniendo calidad y mantenibilidad en toda la solución.

4. **Flutter como framework empresarial:** UI declarativa por widgets, gestión de estado con Provider/BLoC, navegación con Navigator/go_router, formularios con validación y clientes HTTP (http/dio); soporta la complejidad de un dashboard con mapas, tablas de indicadores y reportes.

5. **Concurrencia y rendimiento:** El backend con pool de conexiones (HikariCP) y consultas JPA optimizadas atiende el dashboard en tiempo real y el volumen de 1,000 pedidos diarios / 50 vehículos; el cómputo intensivo de la metaheurística (≤ 45 s) se aislará en hilos dedicados sin bloquear las peticiones (ver ADR-03 en DOC-012).

6. **Optimización con ecosistema JVM:** La metaheurística (Algoritmos Genéticos, Búsqueda Tabú, Colonia de Hormigas o Enfriamiento Simulado) se implementará en Java dentro del mismo backend para resolver VRPTW/Green VRP dentro del requisito de ≤ 45 segundos.

7. **Costo de infraestructura moderado:** El MVP corre monoinstancia (API + PostgreSQL), alineado con el presupuesto de S/ 500,000 y el LCC a 3 años; el escalado horizontal queda como arquitectura objetivo (ver DOC-012 §5).

8. **Restricciones de código abierto:** Spring Boot, Flutter y PostgreSQL son tecnologías de código abierto, cumpliendo la restricción RES-07 del proyecto.

9. **PostgreSQL:** Relacional, con soporte geográfico (PostGIS) para cálculos de rutas y coordenadas GPS, y capacidad de escalamiento horizontal.

10. **Reutilización de widgets:** Flutter permite construir widgets reutilizables (mapa, dashboard, formularios de pedidos) acelerando los RF-004, RF-005 y RF-010.

11. **Arquitectura cliente-servidor:** La solución se estructura como **cliente-servidor**: el frontend Flutter (SPA web para operador/dashboard y modo móvil para conductor, con caché offline) actúa como **cliente** y consume la **API REST de Spring Boot** (servidor único) mediante HTTP/HTTPS JSON. Esto separa responsabilidades entre presentación y lógica de negocio, permite escalar el servidor independientemente del cliente y respalda los requisitos de concurrencia, integraciones externas y re-optimización.

### 2.2 Componentes del stack

| Capa            | Tecnología              | Justificación                                                 |
| --------------- | ----------------------- | ------------------------------------------------------------- |
| Backend (único) | Java 17 + Spring Boot 4.1 | seguridad, validación, JPA, Flyway, OpenAPI integrados |
| Frontend        | Flutter (Dart)          | UI declarativa por widgets, hot reload, multi-plataforma (web + móvil) |
| Base de datos   | PostgreSQL              | relacional, soporte geográfico (PostGIS), 3FN                 |
| Mapas           | flutter_map + OpenStreetMap | código abierto, gratuito, cumplimiento RES-06                 |
| Caché           | Redis (objetivo, no implementado en MVP) | sesiones y caché de consultas frecuentes                      |
| Autenticación   | JWT HMAC-SHA256 + refresh rotativo | OWASP; sin IdP OAuth2 externo en el MVP                       |

**Alternativas descartadas:** MEAN con MongoDB (base de datos no relacional menos adecuada para integridad transaccional y rutas geográficas). **Node/Express + TypeScript** (selección de V_1_3_0, revocada en V_1_4_0): la reescritura descartaba autenticación, RBAC, validación y 49 pruebas ya implementadas y verificadas en Spring Boot; ver ADR-07 en DOC-012. **FastAPI no se considera:** el backend del proyecto es **único**.
